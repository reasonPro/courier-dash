# CourierDash — план розвитку та технічний журнал

## 1. Призначення документа

Цей документ є єдиним актуальним джерелом інформації про:

- поточний стан проєкту;
- завершені роботи;
- активну задачу;
- заплановані етапи;
- прийняті технічні рішення;
- відомі проблеми;
- результати перевірок;
- питання, які очікують рішення.

Одночасно активною може бути лише одна технічна підзадача. Після завершення кожного етапу потрібно оновити його статус, результати перевірок і журнал виконання.

## 2. Головні правила безпеки

- Не ламати функціонал, який уже працює.
- Перед кожним завданням фіксувати початковий стан.
- Одна задача — одна окрема feature або fix гілка.
- Не змішувати в одному завданні рефакторинг, виправлення помилок, переклади, зміни бази даних і новий функціонал.
- Якщо є неоднозначність, яка впливає на поведінку, зупинитися та поставити запитання до реалізації.
- Не приймати самостійних рішень щодо фінансових формул, податків, структури бази, даних користувачів, сумісності localStorage або поведінки UI.
- Кожну зміну структури Supabase виконувати через окрему міграцію.
- За можливості зберігати зворотну сумісність зі старими записами.
- Ніколи не використовувати Supabase `service_role` у клієнтському коді.
- Не виконувати commit, merge, push або deployment до ручної перевірки власником проєкту.
- Віддавати перевагу малим послідовним змінам, а не великому переписуванню.
- Не видаляти старий робочий код, доки його заміну не перевірено.
- Не змінювати існуючі localStorage-ключі без окремого рішення та плану сумісності.
- Не змінювати фінансові формули в межах технічного очищення або типізації.
- Перед змінами бази визначати вплив на старі записи, місячний звіт, річний звіт і майбутній мобільний застосунок.

## 3. Ролі

### Власник проєкту

- визначає потрібний функціонал;
- приймає продуктові рішення;
- затверджує важливі технічні рішення;
- вручну перевіряє поведінку сайту;
- дає дозвіл на commit, merge і push.

### ChatGPT

- планує етапи;
- аналізує архітектуру;
- готує промпти для Codex;
- аналізує відповіді Codex;
- допомагає оцінювати ризики;
- координує оновлення roadmap.

### Codex

- аналізує репозиторій;
- виконує тільки затверджене завдання;
- запускає автоматичні перевірки;
- надає структурований звіт;
- не приймає неузгоджених продуктових або архітектурних рішень;
- не виконує commit, merge, push або deployment без окремої команди.

## 4. Завершений функціонал

- Підтримка Stuart.
- Підтримка платформи Other.
- Гнучкий вибір активних платформ.
- Вибрані платформи зберігаються в localStorage.
- Сторінку Work розділено на компоненти.
- Онлайн-чайові та готівкові чайові враховуються окремо.
- Мобільний заголовок чайових налаштовано для української, англійської, польської та російської мов.
- Використовується Git-процес: feature або fix гілка → перевірка → commit → merge у main → push → автоматичний deployment у Vercel.
- Вибрана мова застосунку зараз зберігається між відвідуваннями.

Локалізація Garage та Annual Report ще не завершена.

## 5. Відомі проблеми

- Попередній ESLint-аудит показав 23 помилки та 2 попередження.
- Попередній аудит виконувався на гілці `refactor/work-page-components` і включав незакомічені файли рефакторингу, тому результат потрібно повторно перевірити на актуальному стані репозиторію.
- Garage перекладено не повністю.
- Annual Report перекладено не повністю.
- Annual Report ще не враховує всі поля та значення, які доступні в місячному звіті.
- Повний модуль витрат ще не реалізований.
- Податки та розрахунок Netto ще не завершені.
- Для мови та налаштувань із localStorage є React lint-зауваження, пов’язані з SSR і гідрацією.
- У коді Chart.js є `explicit any`, які потрібно виправляти окремим контрольованим завданням.
- У майбутньому можуть додаватися нові:
  - розрахунки;
  - фінансові показники;
  - колонки бази даних;
  - платформи;
  - витрати;
  - податкові правила;
  - звіти;
  - функції Garage;
  - мобільний застосунок.

## 8. Журнал прийнятих рішень

- Розробка виконується малими контрольованими етапами.
- Одночасно активна лише одна технічна підзадача.
- Кожен етап має окремий аудит, реалізацію, перевірку і Git-крок.
- Фінансова логіка не змінюється під час lint cleanup.
- Система збереження вибраної мови повинна залишитися сумісною з наявними користувачами.
- Нові колонки Supabase додаються лише через міграції.
- Річний звіт функціонально завершується після витрат і податків.
- Архітектурні зміни виконуються поступово, без великого переписування.
- Нові функції повинні по можливості використовувати спільні типи, сервіси й розрахункові функції.
