## Обов'язковий порядок роботи

Для кожного нового завдання:

1. Спочатку коротко дослідити лише пов'язані з ним місця.
2. Надати користувачу короткий план максимум із 5 пунктів.
3. До повідомлення користувача `ЗАТВЕРДЖУЮ` не редагувати файли та не виконувати дії, що змінюють стан. Read-only перевірки дозволені.
4. Після затвердження самостійно внести всі необхідні пов'язані зміни в межах погодженого плану.
5. Запустити доречні перевірки й коротко повідомити результат.

## Зміни Supabase

- Кожну зміну схеми, даних, функцій, тригерів або RLS спочатку оформлювати як окрему SQL-міграцію.
- Перед застосуванням пояснювати, що саме робить міграція та які об'єкти зачіпає.
- Не застосовувати міграції та інші зміни до віддаленої бази без окремого явного підтвердження користувача.
- Read-only інспекція віддаленої схеми дозволена в межах погодженого завдання.

## Постійна домовленість: одна робоча папка

- Працюємо у звичній папці `courier-dash`; задачі розділяємо Git-гілками.
- Перед переходом зберігаємо tracked і untracked роботу в її власній гілці. WIP/checkpoint не означає приймання задачі.
- Наявні linked worktrees залишаються архівами; нові worktrees створюємо лише на пряме прохання власника.
- Локальний запуск: `npm run dev`, `http://localhost:3000`, справжні сторінки застосунку. Окремі demo-сторінки та спрощені копії UI — лише на пряме прохання.
- Чинний дизайн зберігаємо, крім конкретно погоджених елементів.
- Порядок приймання: локальний справжній застосунок → окремо погоджений Preview → окремо погоджений Production.
- `localhost` НЕ гарантує тестову базу. До запуску перевіряємо Supabase target без показу секретів; тестові записи дозволені лише в явно погодженому тестовому середовищі.
